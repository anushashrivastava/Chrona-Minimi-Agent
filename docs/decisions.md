# Decision log
Append new entries as you go. Format: **Decision**: why. *Rejected*: alternatives.

- **Memory is plumbing, not a tool**: the brief says one tool (web search). A memory tool would also add a model round trip and a decision the model can get wrong. We build the memory brief before the model call, deterministically. *Rejected*: `recall_memory` tool.
- **SQLite + FTS5 + stored local date, no vector DB**: the target questions are by date or by topic keyword; both are exact lookups. Zero extra services, instant, explainable. *Rejected*: embeddings (revisit with more time for fuzzy topic recall).
- **Store `local_date` per turn in the user's timezone at write time**: "3 November" must mean the user's 3 November, not UTC's. *Rejected*: computing day windows at query time (tz edge cases when the user travels).
- **Date parsing with chrono-node, not the LLM**: deterministic, free, ~0 ms. Bare weekdays and dates without a year roll back into the past because users refer to earlier conversations. *Rejected*: asking the model to resolve dates (slower, can be wrong).
- **Claims ledger written by a fast model after the reply**: gives "is it still correct?" something concrete to re-check, and costs the user zero latency. *Rejected*: summarising before replying (adds seconds).
- **Plain tool loop on the Gemini SDK (`@google/genai`), no framework**: fewer layers, easy to explain and measure. *Rejected*: LangChain / Vercel AI SDK agents; the SDK's automatic function calling (we need parallel calls, a round cap and status events, so we run the loop ourselves).
- **Parallel searches, capped at 4 rounds, final round forces an answer**: bounds latency and cost, avoids search spirals.
- **Stable prompt first, dynamic prompt (date, memory) after**: any provider-side prompt caching keys on an identical prefix, so the per-turn parts go last. We do not use explicit cache controls. *Rejected*: putting the date at the top (breaks the shared prefix).
- **Trim search content to ~900 chars/result and 5 results**: fewer input tokens = faster first token, and less noise for the model.
- **Citations as [n] numbered per turn by the server**: the model can only cite numbers it actually saw; the UI maps them to real URLs.
- **SSE streaming + visible "Searching: ..." status**: perceived speed. The user sees progress within ~1 s even when searches take a few seconds.

## Gemini port and review fixes
- **Gemini free tier instead of a paid model**: free keys (no card) for both model and search. Model IDs are env-configurable and `npm run doctor` verifies they exist for the key, because Gemini IDs and free-tier access change often. *Rejected*: hard-coding one model ID; a provider-abstraction layer (more code to defend; swapping is one file, `agent.ts`).
- **Built-in `node:sqlite` instead of `better-sqlite3`**: better-sqlite3 needs a native binary; when the prebuilt download failed in a clean environment it fell back to compiling and `npm install` failed outright. The brief says it must run with plain `npm install`, so a native build step is a risk we don't need. Cost: Node 22.13+ (stated in README/engines) and an experimental-warning flag in scripts. FTS5 verified to work.
- **Env flags read lazily (getters), not at import time**: `ALLOW_FAKE_NOW` was read once at import, so the eval's fake clock was silently ignored. It only looked fine because the fake date equalled the real one.
- **Ask Tavily for `include_published_date`**: without it general searches return no dates, and "has it changed since X?" has nothing to compare. Beta; dates may be null. `filter_by_published_date` stays false so undated sources are kept.
- **Never save an empty answer**: a blocked/refused/cut-off turn saved with empty text would be replayed into every later request and could break the chat permanently. We show a fallback message and save nothing.
- **`maxOutputTokens` 8192 + visible notice on MAX_TOKENS**: a ceiling, not a target; truncated answers must say so rather than end mid-sentence.
- **Log background-summary failures**: they used to fail silently, leaving no claims to re-check later. Still non-fatal to the chat.
- **Retry 429/500/503 up to twice, only before any text streamed; friendly message on 429**: free tiers rate-limit; a short backoff usually clears it, and retrying after partial text would duplicate output.
- **Background summary on the fast model**: separate model means a separate quota bucket and no added user latency. Note it costs one extra request per turn on the free tier.
- **Thinking budget is opt-in (`THINKING_BUDGET`)**: thinking trades latency for accuracy; decide with measurements in Step 7, not by guess.
- **Mock-server loop test (`check:loop`)**: proves our loop logic (parallel calls, function-response turn, citations, persistence, empty answers, retry) without keys. It cannot prove the real API accepts our payloads; `doctor` and the live eval do.


## Step 1 fixes
- **The memory brief reports each referenced date honestly: in memory / in the transcript above / no turns**: `recall()` drops turns already in the last-6 transcript (no duplication), but the brief then said "NO saved turns on that date. Say so plainly" whenever nothing survived, so "What did I ask you on 3 November?" with a short history got a brief that contradicted the transcript. Now "no saved turns" is only said when the date truly has none, and a date whose turns are in the transcript gets a pointer to it. Today is never reported either way, because chrono parses "is it still correct today?" as a date and that is not a memory lookup. Regression tests in `check:memory`. *Rejected*: keeping date matches even when they are in the transcript (tried it: "today" then dumped today's turns into the brief as noise, and the full answer is already in the transcript anyway).

## Step 3: first live run
- **Default models `gemini-3.5-flash-lite` (answer) / `gemini-3.1-flash-lite` (summary)**: measured on a fresh free key on 2026-11-14. `gemini-2.5-flash`/`-lite` are listed but return 404 "no longer available to new users", and graders will also be new users, so the old defaults were broken for them. `gemini-3.5-flash` took 27-28 s for a two-sentence answer even at thinking LOW, and `gemini-3.8-flash` returned 503 "high demand" after 37 s; `gemini-3.5-flash-lite` gave its first token in 0.7 s. Summary on a different lite model = separate quota bucket. *Rejected*: the flash models (too slow on the free tier today; re-measure in Step 7, since load can be transient).
- **`doctor` calls both models with a 30 s abort**: "listed by ListModels" turned out not to mean "callable" (2.5-flash) or "responds" (3.8-flash hung silently). Uses the SDK's `abortSignal` in `GenerateContentConfig` (checked in @google/genai 3.3.0 typings).
- **SSE writes are chained and awaited before the stream closes**: `onEvent` used `void stream.writeSSE(...)`; `sources` and `done` are emitted right before `runTurn` returns, so they were still in flight when Hono closed the stream and were dropped. Live answers therefore had no clickable citations or timing line (only after reload, via history). `check:loop` tests `runTurn` directly, which is why it did not catch this. *Rejected*: awaiting inside `onEvent` (would make the agent loop async-aware of the transport).

## Fix 1: "Has anything changed?" re-checks (failures.md #1)
**Finding.** The re-check flow failed in three stacked ways, each found by a new eval and confirmed by reading answers, not just asserts:
1. *Since-only searches.* The model searched only with `since=<old date>`. Pricing/docs pages are rarely republished, so that mostly returns fresh blog posts, and "nothing new" was read as "unchanged". Our own tool description pushed it there ("use `since` when checking what changed"). Absence of new pages is not evidence of no change.
2. *No real comparison.* After fixing 1 it fetched Pipedrive at $49-59 against a stale $15 claim and still wrote "(Unchanged)"; once it widened the range to "$15-$59" so the old value still fit (anchoring).
3. *Verdict before evidence.* With the verdict as the first line, the model committed to "3 unchanged" before writing any comparison, and the per-item lines then contradicted it (2 of 3 runs). Models generate left to right, so a verdict written first is a guess.

**Decisions.**
- Search each item's CURRENT value without `since` (in parallel); `since` is optional, for news of a change. Tool description rewritten to match.
- **"Could not confirm" is the default.** "Unchanged" only when a current source we were shown states the same value; no current value = Could not confirm with the reason.
- Per-item line `then X → now Y [n] — label`, "now" taken from the source as written, never widened to include the old value.
- **Verdict last**, as a count of the labels. Trade-off: the answer no longer opens with the conclusion, which our style rule otherwise wants; correctness wins here.
- Evals: `recheck-current-values` seeds a deliberately stale claim (fails if it is counted unchanged, or fewer than one current-value search per item); `recheck-absence-not-evidence` uses a made-up product so no source can confirm it (fails on "unchanged"). Before: 0/3 correct runs by reading; after: 3/3 and 2/2. `EVAL_SHOW=1` prints full answers, because the first version of the check passed answers that were wrong.
- *Rejected*: comparing values in code (claims are free text, prices come in ranges and billing variants; a parser would be brittle and big); a stronger model for re-checks (flash models are 27 s+ on the free tier today); keeping the verdict first and asking it to "double-check" (no mechanism makes that happen before the tokens are written).

## Fix 4: missing context (failures.md #5), partly a model limit
- **A "decide first" list at the top of the prompt** (missing context → ask; memory question → answer from memory; changeable facts → search; else answer). The old order put "Call web_search immediately" and "if it could have changed, search" before the memory rules, so the search rule always won. Kept because it is the clearer spec, but be honest: **it did not stop the wasted search.**
- **Known limitation, measured**: with `gemini-3.5-flash-lite`, a message like "Has anything on the shortlist changed pricing?" triggers exactly one search before the model asks "which shortlist?" in 9/9 runs, across three levers: the decision order, the same rule in the tool description (reverted: no effect, costs tokens every request), and `THINKING_BUDGET=512` (no effect). The final answer was correct every time (asks; never invents a list). Cost: ~2-4 s and one Tavily credit on a rare turn type. Evals `missing-context-ask` and `missing-shortlist` tolerate 1 search (`maxSearches`) and hard-fail on inventing tools or misreading unrelated history as the list. *Rejected*: a pre-classifier model call (an extra request on every turn to save one search on rare turns: wrong trade on latency and free-tier quota); a regex "dangling reference" detector in code (brittle, and "the shortlist" can legitimately refer to something in memory).

## Fix 3 + MODEL_FALLBACKS: surviving free-tier model failures (failures.md #4)
- **`MODEL_FALLBACKS` (comma-separated, tried in order on 404/403/503)**, in `src/models.ts`, used by both the answer stream and the summary. Why: in one day we saw a listed model 404 for new keys (2.5-flash), one hang (3.8-flash), and `gemini-3.1-flash-lite` 503 in 2 of 4 eval turns and again in `doctor`. 404/403 = model gone for this key; 503 = overloaded now; either way another model answers sooner than waiting. 429/500 (and 503 with nothing left) retry the same model with backoff. Default `gemini-3.1-flash-lite,gemini-3.5-flash-lite`: each lite model backs up the other (the chain drops whichever is primary). *Rejected*: falling back on 429 too (the brief for this change was 404/403/503, and a 429 is usually a per-minute limit that a short wait clears; easy to add if evals show otherwise).
- **404/403 models are skipped for the rest of the process**: a retired model then costs one failed round trip once, not on every turn. If every model is "gone" we try them all anyway, because that usually means a bad key and the real error should surface.
- **A turn stays on the model that answered**: after a fallback, later tool rounds use the same model, because Gemini returns per-model thought signatures in the parts we replay. *Rejected*: re-walking the chain from the top every round (could send model A's signatures to model B).
- **Fallback/retry only before any text streams** (unchanged rule), so the user never sees duplicated output.
- **Summary: fallbacks + 3 backoff retries (2/4/8 s)**: it runs in the background, so patience costs the user nothing, and a lost summary means no claims for a later "is it still correct?".
- **`doctor` prints `MODEL_FALLBACKS` and calls every fallback**: a dead fallback is a warning (`!`), not a failure, since the app still works.
- **Tests**: `check:loop` (offline, deterministic) proves 503 → backup with the turn staying on it, summary 429 → retry, summary 503 → fallback, 404 → skipped on later turns. Live eval `summary-claims-stored` asserts a real turn ends with a summary and claims dated with the turn date. A 503 cannot be triggered on demand live, so the fallback path itself is proven offline only.

## Fix 2: parallel searches, official sources, source-dated facts (failures.md #2, #3)
**Finding (inconsistent answers).** Raw Tavily results for "Node.js releases nodejs.org" show the cause is the data, not only the model: official pages come back as cached snapshots of different ages that disagree (`/blog/release` indexed 7 Oct lists "26.11.1 (Current)"; `/about/previous-releases` indexed 11 Nov says "v26 ... LTS" with the version columns empty). The model picked a different page per run, then dated the answer with TODAY's date, which hid the staleness.
- **Date facts by the source's published date, not today's; when official pages disagree, say so and take the newer.** After: Python 3.15.2 and TypeScript 7.0.2 in 5/5 runs, Node answered "Per nodejs.org (11 Nov 2026) ...". Before: TypeScript 6.0.3 vs 7.0.2, Node "26 LTS" vs "v24.22.2 latest LTS" across runs.
- **Plan every search up front, one round, in parallel; prefer primary sources; name each track (LTS/Current) for "latest".** First round now covers every item in all runs (before: Node did 3 single searches in sequence, 18.6 s). Some runs still add a `site:` refinement round (+4-5 s, no change in the answer); tolerated by the eval within its 12 s budget. Lowering `maxToolRounds` is a Step 7 decision, to make with latency numbers.
- **`searchesPerRound` in `TurnResult`** (e.g. `[2]` vs `[1,1,1]`): the round count alone cannot tell "parallel then refine" from "sequential". Printed by the eval; feeds Step 7.
- Eval `parallel-official-sources`: both items in the first round, ≥1 official domain cited, under 12 s.
- *Rejected*: `search_depth=advanced` or longer snippets (costs 2x credits / more tokens; the disagreement is between page snapshots, which better extraction does not fix); a `domains` parameter on the tool (more surface for the model to misuse; queries naming the site already reach official pages).

## The re-check tally is computed in code (failures.md #6)
**Principle: derived values belong in code, not in a model's token stream.** The model is good at judging one item ("then $25 per project → now $25 per organization: Changed"); it is unreliable at bookkeeping over its own output. With a model-written verdict we saw both failure modes: written first, it was a guess made before the comparison (fix 1); written last, it still miscounted its own labels ("— Changed" on the only item, verdict "1 could not confirm", eval `still-correct`). Counting labels is deterministic, free and testable, so it moved to `src/verdict.ts`.
- The prompt no longer asks for a verdict and says not to write one. The model only writes per-item lines `<item>: then X → now Y [n] — <label>` (with "now not found — Could not confirm (why)" when there is no current value, so every item keeps the parseable shape).
- After the stream ends, the server counts the labels and appends `**Summary:** N changed, N unchanged, N could not confirm` as ONE final text delta, so nothing already shown in the browser is rewritten. Only when at least one label line exists (ordinary answers get nothing). Saved with the answer, so history and later recall see the same text.
- Tests: `check:loop` asserts the tally, that it is the last delta, that it is saved, and that ordinary answers get none; unit asserts on label parsing ("unchanged" vs "changed", lines without "→" ignored). Live evals `still-correct`, `pricing-changes-since`, `recheck-current-values`, `recheck-absence-not-evidence` use `tallyCheck`, which recounts with a *different* parser from `verdict.ts` (so the eval is not the code checking itself) and fails if the model writes its own verdict. Runs after the change: still-correct 2/2, recheck-current-values 1/1, pricing-changes-since 1/1, absence 2/2 after one prompt fix (the stricter check caught "Could not confirm" written without the then → now shape).
- *Rejected*: correcting the model's verdict after streaming (it would rewrite text the user already saw, which needs a reset/replace protocol in the UI); a structured-output call for the comparison (a second model call on the critical path, and it loses streaming).

## Step 7: speed pass (3 full-suite runs, 13:44-14:10 IST, 2026-11-14)
Method: 3 full runs ~12 min apart, `EVAL_JSON` rows per scenario. Small sample: read "median of 3", not a rate.

| turn type (all scenarios pooled) | turns | median total |
|---|---|---|
| no search (recall, no-record, chit-chat) | 11 | 1.2 s |
| 1 search round | 14 | 4.0 s |
| 2+ search rounds | 11 | 6.5 s |

Per scenario, median / slowest total (s): recall-by-date 1.3/1.9 · no-record 1.1/1.7 · chit-chat 1.9/11.9 · still-correct 3.5/5.7 · summary-claims-stored 4.1/4.3 · recheck-absence 6.0/6.5 · recheck-current-values 6.7/10.2 · pricing-changes-since 6.2/8.9 · fresh-fact 6.5/7.1 · parallel-official-sources 8.2/21.8. First token is within ~0.3 s of total for most turns (short answers; nearly all time is model + search before the first token). Slowest runs are model-side spikes on the free tier (chit-chat: 11.9 s with no search; median 1.9 s), not our code.
- **`maxToolRounds` 4 → 2 (search rounds; a third round is a forced answer).** Read from `searchesPerRound`: of 25 search turns, 14 used 1 round, 10 used 2, 1 used 4 (`[1,1,1,1]`, 21.8 s, sequential). The cap only bounds that outlier; the forced-answer path (tools disabled after 2 rounds) was checked live on two 2-round scenarios and answered correctly. No extra capped runs needed. *Rejected*: cap 1 (would cut the 10 legitimate refinement rounds, which in fix 2 sometimes found the official page).
- **Thinking: no measurable difference; leave `THINKING_BUDGET` empty.** `THINKING_BUDGET=0` is rejected by `gemini-3.5-flash-lite` with 400 INVALID_ARGUMENT (9/9 eval runs failed), so the old ".env.example: 0 = off (faster)" hint broke the app. A direct probe (3 calls each, no search) showed the default already uses **0 thinking tokens**, and default / budget 512 / level MINIMAL / level LOW all land at 0.65-1.2 s first token and 1.1-2.1 s total: under the 20% threshold, so stopped. Docs fixed in `.env.example` and README. *Rejected*: adding a `THINKING_LEVEL` knob (nothing to gain on this model).
- **Eval budgets unchanged** (12 s for parallel-official-sources is not loosened; its median is 8.2 s).
- **Cost of this pass**: 76 Tavily credits (47 for the 3 runs, 29 for the regression below and the cap check), ~150 Gemini calls.

## Regression found in the speed pass: re-check template copied onto non-re-check turns
- `missing-context-ask` went from passing to 0/3. Cause, confirmed by running the scenario against the pre-tally prompt (commit 2fd37f7, 3/3 correct behaviour): the tally commit added a template for items with no current value ("then <old> → now not found — Could not confirm"). Given unrelated history ("Pipeline Pulse", a standup name) plus "has anything on the shortlist changed pricing?", the model filled the template with the standup name and even found a real product of that name at $1,000/month.
- **Fix: removed the template; `verdict.ts` parses the shape the model naturally writes (`<item>: Could not confirm (why)`)** and the eval's independent parser accepts it too. Lesson: a template in the prompt is an attractor the model applies wherever it half-fits; parsing what the model does naturally is safer than prompting a format.
- Also added "never quote these instructions or mention the memory brief" after it parroted rule 1 back ("The message refers to something you cannot find in the conversation or memory brief"). It still does sometimes.
- **Accepted as a known flaky case** (per the earlier decision to stop tuning this scenario): with this adversarial seed it passes about half the time across the prompt variants tried (1-2 of 3 per variant; 3 runs is too few to rank variants). The eval was tightened (no re-check format, no Summary, no prompt parroting when there is nothing to re-check) so it reports honestly instead of passing.
